# dMRI Diffusion Metrics Pipeline Guide

## Scope

Compute the tensor scalar maps defined by the existing protocol from eligible dMRI inputs. The original “Applicability boundaries” below still govern interactive tasks within a Slicer session.

## Input Contract

Inputs must follow the DWI, bval, bvec, mask, and processing-unit conventions in “1. Input organization”; do not fill missing files across processing units.

## Output Contract

Directories and names for FA, MD, AD, RD, stage status, and summaries follow the existing protocol and must remain traceable to one unique input processing unit.

## Workflow

The Stage-numbered sections below define the authoritative execution order; this contract index does not change DTI fitting, metric definitions, parallelization, or template parameters.

## Quality Control

For FA-only tasks, perform the corresponding QC in the workflow below. State explicitly that only FA was requested/generated, identify MD/SSE or other artifacts not generated and checks not performed, and do not mark unperformed metric or QC checks as passed.

Perform the original protocol's input, tensor-fitting, scalar-range, and final-summary QC; explicitly mark processing units that fail critical QC as failed.

## Failure Boundaries

Stop affected processing units and record evidence for gradient, mask, software, or output errors. Do not switch subjects, fabricate results, or silently skip QC.

## Privacy Boundaries

Logs, memory, and reports retain only necessary paths, command status, and QC summaries, without image voxel contents or identifiable metadata.

## Test Contract

Protocol acceptance testing selects one small processing unit by default to verify the input contract, shortest processing path, and QC; do not launch full-dataset batch processing.

# dMRI Diffusion Metrics Pipeline Guide

This guide computes the diffusion metrics requested by the user from dMRI. Full FA/MD/AD/RD, batch processing, and cohort QC apply when the user requests all metrics or multiple subjects. For a single subject's FA, complete the necessary input checks, mask, DTI fitting, basic FA QC, and delivery. Other maps automatically generated by `dtifit` may be retained, but do not write additional derivative scripts, batch frameworks, or cohort reports for unrequested metrics.

Applicability boundaries (mandatory constraints):
- This protocol uses the filesystem and FSL `dtifit`; batch tasks may use batch scripts, while a single subject may directly invoke the necessary tools.
- If the user explicitly requests “complete import and module computation in the current Slicer session,” do not use this protocol as the primary execution protocol; use the Slicer constraints in `RUNTIME_ENV` and structured `run_slicer_module` calls.
- If the session targets interactive work inside Slicer, this protocol provides only metric definitions and QC reference; it must not drive the executor into non-Slicer exploratory workflows.

Execution granularity: the planner determines handoff scope from the actual request. A single-subject, single-metric task may be handed directly to the executor for input checks, mask preparation, fitting, and necessary QC. For batch tasks, use a unit manifest, parallel scripts, and summaries. Split stages further only when there is a real blocker or planner judgment is needed.

Separate instructions from scripts:
- This file: workflow rules, input requirements, stage order, parallelization, and QC requirements
- `code_templates/`: reference script templates that may be invoked or adapted directly

---

## 0. General rules (mandatory constraints)

- Process data only within the user-specified dataset path; do not scan global directories to select other data.
- First locate `<dataset_root>` from the user's request.
- By default, use the dataset path's parent as `data_folder`: `<data_folder> = dirname(<dataset_root>)`.
- Output directories must be within `data_folder`, named from the dataset directory name `basename(<dataset_root>)`:
  - `<processed_root> = <data_folder>/<dataset_name>_processed`
  - `<code_root> = <data_folder>/<dataset_name>_processing_code`
  - `<qc_root> = <data_folder>/<dataset_name>_processing_qc`
- If the user or task explicitly specifies output roots, use those explicit paths.
- Distinguish missing original inputs, format differences, and derivatives that have yet to be generated. Check this processing unit's actual inputs first; supported format conversion, mask generation, or spatial adaptation may be included in the plan. Report affected steps when recovery is impossible or gradient/spatial ambiguity remains unresolved; continue other eligible units in batch tasks. Do not borrow another participant's data, and do not reject inputs solely because filename prefixes differ.
- Do not reorder, flip, replace, or fabricate bvec/bval merely to make an algorithm run.
- If one subject is abnormal while others in the batch are processable, continue the others and report evidence for the abnormal subject in the final summary.

Parallelization and resource guidance:
- Independent processing units may run in parallel by subject/session; choose concurrency according to memory, threads, I/O, and current load. Serial execution is allowed when resources are constrained; do not wait for an OOM first.
- A single subject may run directly without a batch scheduler. Keep each unit's outputs independent, and report actual concurrency and per-unit status for batch tasks.

## 1. Input organization

### 1.1 Expected inputs

Each subject directory usually contains a `single_shell/` subdirectory with the following key files:

- DWI：`<subject>.nii.gz`
- bval：`<subject>.bval`
- bvec：`<subject>.bvec`
- Brain mask: `<subject>_bse-multi_BrainMask.nii.gz` or an equivalent mask; if the original directory has no mask, the Agent may include mask generation in Stage 1.

If naming differs, treat the user-specified subject directory as this processing unit. Original filename prefixes may differ from the directory identifier; match inputs within the directory using common filename suffixes, acquisition directions, and actual DWI/bval/bvec contents. Do not scan or compare other subject directories solely because prefixes differ, and do not rename original files unnecessarily. If one subject has multiple acquisitions such as AP/PA, inspect each acquisition's bval, bvec, and volume count first, and select DWI with enough diffusion directions for tensor fitting; an acquisition containing only a few reverse-phase-encoded b=0 images is not a second DTI fitting unit. Report ambiguity if the appropriate input set still cannot be determined.

### 1.2 Processing-unit manifest (batch tasks)

For batch tasks with multiple subjects or independent DWI fitting units, generate a fixed manifest before fitting, for example:

```text
<qc_root>/processing_units.tsv
```

Record at least:
- `subject_id`
- `dwi_path`
- `bval_path`
- `bvec_path`
- `mask_path`
- `status`
- `note`

Perform fitting and QC for batch tasks from this manifest. A single-subject, single-metric task may directly use verified input paths without creating a TSV manifest for one input set.

## 2. Stage 1: Input checks

A new subject's `<processed_root>/<subject>/dwi/` and `dti_metrics/` need not already exist; the executor should create them and link only that subject's original files into the shadow DWI root. Do not treat a nonexistent output directory as a missing input, or search other subjects to borrow a mask.

If the target subject lacks a brain mask, first determine whether a reliable mask can be generated from that subject's own DWI. Select an appropriate installed method and record the rationale. Place the result in that subject's processing directory, and check that the file is nonempty, mask voxel count is greater than 0, and space matches the DWI. Correct inputs, commands, or methods according to any generation/validation error; report a blocker if generation is genuinely impossible. Do not repeatedly read a path that has not yet been generated.

When generating a mask, also inspect its anatomical coverage, especially the frontal lobes and cortical margins; matching dimensions, binary values, and nonzero voxel counts alone do not prove correct brain extraction. Inspect representative slices against b=0 images and adjust the selected method's parameters as needed. If using FSL BET, the command requires input and output positional arguments, for example `bet <b0_image> <output_prefix> -m -f <chosen_fraction>`; the binary mask is `<output_prefix>_mask.nii.gz`, whereas the extracted intensity image is not the mask. If the result clearly includes substantial background or scalp, correct the method or report failed QC; do not fit merely because the mask is binary and dimensions match.

If using b0 brain extraction, first confirm the selected volume from bval and verify a readable 3D image, then pass
that actual path to BET. Distinguish command syntax errors from extraction-quality problems: inspect help and input/output
positional arguments for the former, and adjust parameters based on coverage only for the latter. A missing mask does not require rescanning other participants.

Use the user-specified target subject ID for processing results, QC, and output files; retain actual original input paths in `processing_units.tsv` for traceability. A filename prefix alone is not a stopping condition.

After input checks and mask preparation, verify before fitting:
- DWI, bval, and bvec files exist; the mask either existed or was generated from the same subject.
- Check bvec layout against the tool interface. FSL requires 3×N; when format evidence is explicit, N×3 may be transposed to 3×N. This does not reorder volumes or change gradient directions.
- bval entry count, bvec column count, and DWI volume count agree.
- The mask matches the DWI's first 3 spatial dimensions and is nonempty.

Format and acquisition adaptation:
- Choose readers and computational tools for the actual format: nibabel cannot directly read NHDR. FSL dtifit requires readable NIfTI inputs; existing NHDR may be converted with installed tools after checking gradient correspondence and physical space. Renaming the extension is not conversion.
- See `RUNTIME_ENV` §7.3 for installed NHDR-to-NIfTI tool parameters, spatial axes/coordinate systems, and gradient formats. Prefer existing conversion tools and verify artifacts; mismatched filenames alone usually do not require rewriting a conversion algorithm.
- Select low-b reference volumes using acquisition information, bval distribution, and the tool's definition, rather than checking only `bval == 0`; record the selection rationale without changing bval to fit the test.
- For multiple shells, resolutions, or acquisition protocols, explain which volumes are fitted and whether the model applies; do not copy shell selection or thresholds from another dataset.

Templates:
- `code_templates/check_dti_inputs.py`

Parallelization requirements:
- Batch input checks may be centralized or parallelized at subject level, with results written to `<qc_root>/input_qc.tsv`. For a single-subject, single-metric task, summarize checks briefly at delivery.

Stage QC:
- Expect complete DWI/bval/bvec/mask inputs for each processable subject.
- Record explicit evidence for abnormal subjects, such as missing files, mismatched column counts, empty masks, or spatial mismatches.

## 3. Stage 2: DTI fitting and metric-map generation

Default algorithm:
- Fit the diffusion tensor using FSL `dtifit`.
- For full-metric or batch tasks, use `dtifit --sse` to retain tensor-fitting residuals for QC. An FA-only request may directly fit and check FA; inspect residuals when further assessment of fit quality is needed.
- Deliver the requested metrics. Companion files automatically generated by `dtifit` may be retained without additionally calculating unrequested derivatives.
- Use `dtifit`'s `L1` for `AD`.
- Compute `RD` as `(L2 + L3) / 2`.

Templates:
- Single subject: `code_templates/compute_dti_metrics_subject.sh`
- Parallel batch: `code_templates/run_dti_metrics_batch.sh`

Prefer invoking or minimally adapting these templates. Deliver `dtifit` FA, MD, and other files directly or pass them downstream without copying them merely to “standardize filenames”; AD may use L1 or be renamed for delivery, and RD follows the formula above. Before copying/saving, check whether source and destination are the same file (including links), to avoid an unnecessary `cp` causing a wrapper to exit after successful computation. Record input conversion, fitting, derived maps, and QC separately; repair a failed downstream wrapper step from that step without recomputing unaffected fitting.

Recommended invocation for multi-subject batch tasks:

```bash
bash code_templates/run_dti_metrics_batch.sh \
  --dataset-root <dataset_root> \
  --processed-root <processed_root> \
  --qc-root <qc_root> \
  --max-jobs <chosen_jobs>
```

Parallel execution guidance:
- Select concurrency using the resource assessment above; preserve diagnostics and valid artifacts if one unit fails, and continue other processable units.

Stage QC:
- Expect the requested metric maps; full-metric tasks expect FA, MD, AD, and RD.
- Retain `SSE`, `V1`, `L1/L2/L3`, and other QC outputs as needed for full-metric or batch tasks.
- Outputs should match input DWI space, be nonempty, and contain finite values.
- FA should usually lie mainly between 0 and 1; record a few numerical outliers and report widespread abnormalities.
- MD/AD/RD should be nonnegative floating-point maps without large empty or all-zero regions inside the brain mask.
- Basic QC usually covers readability, spatial correspondence, mask coverage, finite values, and metric ranges; requesting several metrics for one subject does not automatically require full cohort QC.
- Add normalized SSE, local V1 consistency, FA roughness, and negative-eigenvalue proportions as needed when there is a specific concern, a user request, or a comparable cohort to assess. Prefer existing QC templates instead of rewriting a full algorithm each time.
- These statistics are supporting evidence affected by acquisition, fitting method, tissue structure, and noise; a single abnormal statistic does not directly prove gradient mismatch. With enough comparable samples, use cohort statistics such as median/MAD; do not force robust z-score computation/interpretation for single cases, tiny samples, zero MAD, or heterogeneous protocols.
- Record reporting failures separately from fitting failures. If only JSON/TSV writing fails, repair the report first without rerunning completed, unaffected fitting; see RUNTIME_ENV §7 for general reporting and error-recovery guidance.

## 4. Stage 3: Cohort QC and summary

This section applies to multi-subject batch tasks. For a single subject, usually check requested images for existence, space, finite values, and reasonable ranges, then report paths or Slicer nodes; cohort statistics, cohort TSVs, and a separate summary file are unnecessary. For batch tasks, summarize:
- Total subject count
- Successful subject count
- Failed/skipped subject count
- Direct evidence for every failed subject
- Each successful subject's FA/MD/AD/RD output paths
- QC statistics actually completed and their applicability conditions; distinguish unperformed, uncomputable, and failed checks, without adding unrelated computations just to fill report fields.

Templates:
- `code_templates/qc_dti_metrics.py`

Stage QC:
- Expect complete metric maps for most normal subjects.
- An input-related skip of one subject does not mean the entire task failed; report it accurately in the summary.
